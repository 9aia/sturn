Source
Expand description

The unified command layer — everything invocable resolves to one grammar, one resolver, every host.

action:<id>              invoke the action (driver dispatch)
route:<path>             host navigation (template over target/params)
host.<builtin>           host capability (filter, help, reload, …)
driver:<name>:<id>       cross-driver action (reserved; resolves locally)

Command::parse turns a command string into a Command; resolve_command maps it plus a ResolveContext (current driver, manifest, view result, sibling-driver manifests, invoke target/params) to a Resolved the host executes:

  • Resolved::Dispatch — send {"op":"invoke"} via crate::Host::invoke (the driver/view/action/target/ params fields are already resolved; declared carries the Action when one was found, for params/danger UX).
  • Resolved::Navigate — interpolate-free route string; the host navigates locally (no wire round-trip). Produced by route: commands, Action::route, and pavo_protocol::ViewSpec::item_route templates.
  • Resolved::Builtin — a HostBuiltin the host implements itself (see BUILTINS for the catalog + suggested keys).
  • Resolved::Unsupported — the command parsed but can’t resolve here (unknown driver, …); display-only.

Route templates ({a.b.c} placeholders) are interpolated by interpolate over a JSON-ish context — see ResolveContext::interpolate_ctx for the shape ({driver, view, target, params, item, data}). ActionResult.route (driver redirect post-invoke) uses the same rules: hosts interpolate it over the invoke context and navigate.

Bindings: declarations suggest, users override. Action::keys, MenuEntry::keys, and BUILTINS default keys are suggestions; a host keymap file (e.g. keys.toml — host config, not protocol) remaps by command id. effective_bindings merges both into the sorted binding list hosts render in help/palette UI; specs validate via crate::keymap::KeySpec.
