Module actions

Expand description

Interaction actions — collection, auto-form mapping, and validation helpers for the invoke wire op.

Actions are declared in three places (all the same pavo_protocol::Action type): DriverManifest.actions[], NodeBase.actions[] on any view node, and TreeItem.actions[] on tree rows. collect_actions folds them into one list a host can render (buttons, palette entries, keybindings) — manifest-global first, then node actions in tree pre-order, then tree-item actions; when ids collide hosts dedupe with item > node > manifest precedence. param_form_field maps a ParamSchema onto the existing FormField widget set so hosts can auto-generate forms; validate_params is the shared client-side check (drivers stay authoritative — ActionResult.errors is the truth).

ops_actions is the zero-declaration fallback: a driver’s ops manifest ({"ops":[{name,doc,params,mutates}]} — the shape pavo-driver-kit’s surface layer parses) derives one action per op, so every ops-manifest driver gets a mutation surface without declaring actions[].

ops_actions
Derive actions from an ops manifest — the zero-declaration fallback. Accepts the raw JSON a driver answers to query "ops" (or <drv> ops argv): {"ops":[{"name"|"query","doc", "params":[{name,kind:arg|opt|flag,doc,schema?}],"mutates"}]}.
param_form_field
Map a ParamSchema onto the FormField widget set — the auto-form half of the interaction layer. ref params degrade to text with a picker hint (hosts with query data may upgrade to a real picker); string[] degrades to comma text.
params_by_name
Sorted param map for tests/debug — params by name.
validate_params
Client-side param validation — required presence, options membership, min/max bounds. Returns per-param error strings keyed by ParamSchema.name (empty map = valid). Pattern checks need a regex dep the core doesn’t carry — drivers enforce pattern authoritatively.
