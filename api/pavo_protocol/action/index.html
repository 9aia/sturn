Interaction actions — the declarative verb layer of the protocol.

An Action is everything a surface needs to offer one interactive operation: a stable id, a label, an optional icon, keyboard keys, typed params (each a ParamSchema — enough for hosts to auto-generate a form), a danger level telling hosts how hard to confirm, and an optional target description naming the context the action needs (an item id, a row, …).

Actions are declared in three places, all the same type:

  • crate::manifest::DriverManifest::actions — driver-global verbs (new item, refresh, …).
  • crate::view_node::NodeBase::actions — scoped to a view node; every ViewNode kind inherits the field.
  • crate::view_node::TreeItem::actions — per-row actions on trees (the only item type with a stable id today).

Hosts render them as buttons (web), keys/palette entries (TUI), or subcommands/flags (CLI) and dispatch through the wire invoke op (crate::wire::Request::Invoke). target on the wire request is opaque JSON — typically the selected row’s raw value or an item id — the driver interprets it.

Actions may also be derived rather than declared: drivers whose ops manifest carries param schemas get actions + auto-generated forms for free (see pavo-core’s ops→actions derivation). Action::params empty means the action takes only its target context.

ParamKind
The input kind a ParamSchema declares — richer than the ops-manifest arg|opt|flag (which maps params onto argv) and wider than crate::view_node::FormFieldKind (which is a renderer hint). Hosts use it to pick widgets: enum → select, bool → toggle, ref → fuzzy picker over a query’s data, string[] → token input.
