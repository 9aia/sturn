Interaction actions (P-032) — the TUI’s side of the invoke protocol.

UiAction is the owned form of pavo_core::ScopedAction the worker ships to the app (scoped actions borrow the view result; the UI needs ’static data across frames). PaletteEntry, PaletteSession, ConfirmSession and TypeTargetSession are the overlay sessions; action_form_spec compiles an action’s params into the existing FormSpec/FormSession machinery so auto-forms reuse the form editor verbatim.

Dispatch flow (InvokeStep): params → auto-form; on submit the collected values are coerce_params-ed and pavo_core::validate_params-checked, then the danger gate runs — none invokes immediately, confirm opens ConfirmSession, type-target opens TypeTargetSession.

The danger: confirm modal — label + description + target hint, y/Enter confirms, n/Esc cancels.
FilterSession
The host.filter overlay — a LineEdit bound to the current view’s filter_param (convention "q"). Submitting re-resolves the view through the normal Cmd::Resolve path with the param set, so drivers see it as an ordinary view param.
PaletteSession
The command-palette overlay: a LineEdit filter over palette_entries, ↑↓/jk selection, Enter activates.
PendingInvoke
An action awaiting (or having passed) the danger gate — what the confirm/type-target sessions carry and what Cmd::Invoke eventually sends.
TypeTargetSession
The danger: type-target modal — “Type <id> to confirm”. Proceeds only on an exact match of the expected id; when the target JSON carries no derivable id, any non-empty input confirms (the value is still shown back in the prompt).
UiAction
An Action plus everything the TUI needs to dispatch it — owned clone of pavo_core::ScopedAction (which borrows the view result the worker collected it from).
