Rail row armed by a first click — a second click opens it.

Open form-editing session (overlay) — Enter on a form field or submit row in the canvas opens one; submit wire op fires from inside it. Also hosts action auto-forms (a FormSession with action set routes to invoke instead).

§actions: Vec<UiAction>

Interaction actions collected for the current view (worker ships them with Ev::View) — palette entries and key chords derive from these.

§menus: Vec<MenuEntry>

contributes.menus[] of the current view’s driver.

§palette: Option<PaletteSession>

Open command palette (: key) — fuzzy filter over actions + menu entries.

§confirm: Option<ConfirmSession>

Open danger: confirm modal.

§type_target: Option<TypeTargetSession>

Open danger: type-target modal.

§pending_key: Option<(String, Instant)>

Pending chord prefix + when it was pressed — multi-char action keys[] specs ("dd") resolve through this; a lone prefix char waits CHORD_TIMEOUT before replaying as a normal keypress.

§key_chords: HashMap<String, Command>

Full key spec → command for bound keys. Specs are normalized KeySpec strings: bare chars/sequences match the char path, ctrl+… chords and named keys (enter, f5, …) match the modified/named-key path. Item-scoped actions are excluded — they carry a row target the canvas doesn’t track, so they stay palette-only.

§chord_prefixes: HashSet<String>

Proper prefixes of multi-char sequence specs — tells chord_or_key whether a lone char might continue into a chord.

§bindings: Vec<CommandBinding>

The merged binding list key_chords was built from — the help overlay’s “commands” section renders this.

§manifests: BTreeMap<String, DriverManifest>

Driver manifests by kind (worker ships them at boot/reload) — the command layer’s ResolveContext table.

§fallback_manifest: DriverManifest

Manifest used when the current driver has none (never in practice — every discovered driver reports one; keeps ResolveContext.manifest total).

§keymap: UserKeymap

The parsed user keymap (keys.toml) — overlay source for effective_bindings.

§view_params: Params

View params of the current/last resolve — route ?query args and the host.filter param live here; refresh and command resolution read them back.

§builtin_menus: Vec<MenuEntry>

Synthesized host.* builtin palette entries (built once — $EDITOR gating happens here).

§filter: Option<FilterSession>

Open host.filter overlay.

§last_dispatch: Option<DispatchCtx>

The last invoke’s dispatch context — ActionResult.route templates interpolate over it.

§auto_refresh: Option<(Duration, Instant)>

Auto-refresh schedule for the current view — (interval, next_deadline) derived from ViewSpec.refresh_ms (bounds-checked). None on the dashboard/notes and for views without a valid hint.

(Re)build key_chords/chord_prefixes/bindings from the unified binding sources: host builtins + menu entries (driver menus and the synthesized host.* entries) + non-item action keys[], merged with the user keymap overlay via effective_bindings. Item-scoped actions are skipped — they carry a row target the canvas doesn’t track, so binding them globally would invoke against the wrong item (they remain palette entries).

An invoke wire-op answer landed. result.view swaps the canvas (with freshly collected actions/menus); without one the host already invalidated its view cache, so a refresh refetches — unless errors rejected the invoke, in which case the status line carries them and nothing navigates.

fn maybe_auto_refresh(&mut self)

Fire the scheduled auto-refresh when its deadline passes. The deadline always slides a full interval forward — a skipped tick (overlay open, resolve in flight) waits rather than bursting on dismiss.
