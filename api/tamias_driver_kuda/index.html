tamias-driver-kuda — pavo view driver for kuda.

Answers the pavo wire ops (manifest, views, view, query) as ndjson JSON-RPC over stdio via pavo-driver-kit’s serve loop — the same {"op":…} / {"ok":…,"result"|"error":…} shape every sibling serve speaks (see pavo/crates/pavo-protocol/src/wire.rs). Also answers the discovery verbs manifest and capabilities as plain argv, plus ops (the engine ops manifest) and run (engine passthrough).

cli <kuda argv> is the tamias bins[] shim verb: tamias bin exec calls it with the standard --dir/--name driver flags ahead of the user’s argv; they’re stripped and the rest runs through kuda::run_from in-process with inherited stdio — full engine parity (watch streams, mcp/acp serve stdio, globals/--help all work).

Optional surfaces: feature mcp embeds pavo-driver-kit’s surface layer — mcp serves the ops as MCP tools on stdio, equivalent to the standalone tamias-driver-mcp surface driver minus the PATH/discovery hop. There is no cli feature: cli is the shim verb above, not a generated surface — the engine’s own argv grammar is the contract.

Repo context: views/queries are read-only — the driver never opens .kuda/index.sqlite for writing. Engine ops are the exception by design: cli.<op> wire queries re-exec the run verb in the request’s repo and let kuda::dispatch own the outcome (cli.sync mutates .kuda/). The repo resolves from the root/dir/path request param, $KUDA_DRIVER_ROOT, or by walking up from the cwd (pavo inherits the user’s cwd, so pavo view kuda:graph inside repo X reads X’s .kuda/).

Install: cargo install --path crates/kuda-driver places tamias-driver-kuda on PATH — pavo discovers it there or under <tamias-home>/drivers/.

Modules§

ops 🔒
Engine ops — cli.<verb> wire queries dispatch into the kuda engine lib through this binary’s own run verb: each call re-execs tamias-driver-kuda run <argv> with cwd set to the request’s repo, so kuda::dispatch writes to the child’s captured stdout and never touches the serve loop’s ndjson stream (the engine’s emit() exits on broken pipe — one more reason ops stay out of the serve process).
queries 🔒
Query implementations — pavo query names mapped onto kuda’s surfaces: kuda-query functions over IndexStore, the committed .kuda/ cards, and drift recomputation (kuda status semantics).
repo 🔒
Repo context — resolve which kuda-indexed repo this request is about, load its config, cards, and L2 store.
views 🔒
Driver manifest + ViewNode trees — the static half of the pavo contract, built with pavo-driver-kit constructors over pavo-protocol types. Keep in sync with pavo/crates/pavo-protocol/src/{manifest,view_node,wire}.rs.

Functions§

dispatch 🔒
One parsed wire Request → response. The kit’s serve loop owns the ndjson plumbing and turns parse failures into ok:false; ops this driver doesn’t implement (render, submit, jobs, notifications) get the same ok:false convention every non-provider driver answers.
engine_argv 🔒
cli verb argv (after the cli token) → engine argv (argv[0] included). tamias bin exec/driver exec prepend the standard driver flags — --dir <payload> --name <pkg> — which the engine doesn’t know; consume the leading run of those two (--flag v and --flag=v forms) and pass everything else through untouched. --config/--workspace are deliberately NOT stripped: they’re kuda globals, so a user-passed one must reach the engine’s own parse.
